# 这样的视频是怎么做出来的

> **对象**：YouTube 频道 `Down From The Moon`（口播署名「辞月赴尘」）SI·LAB 系列 EP.01 / EP.02 / EP.04 / EP.09 四部正片
> **方法**：片源自述 → 工具链一手文档 → 对已下载原片的逐帧实测 → 在本机把整条管线复现一遍
> **一句话结论**：**没有时间轴软件，没有关键帧，没有渲染农场，也没有一个商业软件。整部片子是一个网页项目——HTML 写画面，无头 Chrome 逐帧截图，FFmpeg 编码。**

---

## 本文的读法

这份调研和前面几份技术笔记不一样：前面几份是"读懂片子在说什么"，这一份是"读懂片子是怎么被造出来的"。所以证据的性质也不同，需要分级：

| 级别 | 含义 | 本文中的例子 |
| --- | --- | --- |
| **A 一手** | 片源自己说的、工具官方文档写的、文件头里读出来的 | 简介里的制作自述、HyperFrames 的 CLI 与 HTML schema、`ffprobe` 输出 |
| **B 自算** | 我对原片做的逐帧测量、在本机跑的基准测试 | 60 fps 是否为真、构图节奏、色板、渲染耗时 |
| **C 推断** | 从 A 和 B 反推作者的工作方式，无法直接证实 | 代码行数量级、单人还是团队、具体用了哪个 TTS 音色 |

凡是 C 级判断，文中都会写明"推断"。**没有一处把推断写成事实。**

## 一、它自己承认了什么

四部片子的简介里都有一句固定的话：

> 旁白为 AI 语音合成；标注「AI 生成画面」的镜头与背景音乐为 AI 生成；其余动画均为代码绘制。

EP.04 的英文简介更直接，把工具名都点了：

> Made entirely in code (HTML/SVG rendered with HyperFrames). AI-synthesised narration; a few seconds of AI-generated footage in the cold open (labelled on screen).

这句话已经把片源切成四层，而且是作者主动交代的（A 级）：

| 层 | 占比 | 来源 |
| --- | --- | --- |
| 旁白 | 100% | AI 语音合成 |
| 片头那几秒"实拍感"镜头 | < 1% | AI 生成视频，屏上打「AI 生成画面」标 |
| 配乐 | 100% | AI 生成 |
| **其余全部画面** | **≈ 99%** | **代码绘制（HTML / SVG）** |

关键在于最后一行。观众看到的是"动画效果非常好"，而作者说的是"这些动画全是代码画出来的"。这两句话能同时成立，说明这套做法的完成度已经越过了"一眼看出是模板"的门槛。

**它也点名了工具：HyperFrames。** 这是整份调研的起点——不是我从画面风格猜的，是作者自己写的。所以后面所有关于管线的描述，都可以拿去和官方文档逐条核对，而不是靠看画面倒推。

## 二、HyperFrames 是什么

HeyGen 在 2026 年 4 月开源，Apache 2.0，口号是「Write HTML. Render video. Built for agents.」——最后半句是重点：它是**为 AI 编程助手设计的**，不是为人设计的视频编辑器。

它是一个 npm monorepo，七个包，分工很干净：

| 包 | 职责 |
| --- | --- |
| `hyperframes` | CLI：`init` / `preview` / `lint` / `check` / `snapshot` / `render` / `tts` / `transcribe` |
| `@hyperframes/core` | 类型、解析器、生成器、**linter**、运行时、frame adapter |
| `@hyperframes/engine` | 可 seek 的页面→视频捕获（Puppeteer + FFmpeg） |
| `@hyperframes/producer` | 完整管线：捕获 → 编码 → 混音 |
| `@hyperframes/studio` | 浏览器里的构图编辑器 |
| `@hyperframes/player` | 可嵌入的 `<hyperframes-player>` 组件 |
| `@hyperframes/shader-transitions` | WebGL 着色器转场 |
| `@hyperframes/aws-lambda` | 分布式渲染 |

核心机制只有一句话：**把 HTML 当视频格式**。

- 画面用普通 HTML/CSS 写，时间用 `data-*` 属性声明；
- 动画用 GSAP（或 CSS / Lottie / Three.js）写，但**时间轴必须是 `paused: true` 并注册到 `window.__timelines`**；
- 渲染时，无头 Chrome 打开这个页面，**一帧一帧地问它"第 n 帧长什么样"**，截图，最后交给 FFmpeg 编码。

这个设计里唯一真正重要的取舍是**确定性**：同样的输入，必须产出同样的帧。这一条决定了后面的一切，我在第四节单独讲。

## 三、管线全貌：七步

![一条片子的七步：脚本 → TTS → 转写 → 写构图 → 检查 → 逐帧渲染 → 编码混音](images/fig01_pipeline.png)

拆开看是这样：

**① 脚本。** 中文口播稿，按"一个意思一段"切。这一步没有工具，是写作。

**② 合成旁白。** `npx hyperframes tts <script>`。内置的是本地 Kokoro-82M 模型，**不需要 API key**，`--lang zh`，音色 ID 首字母 `z` 代表中文。可调 `--speed`。

**③ 转写回时间轴。** `npx hyperframes transcribe`。引擎可选 Parakeet 或 Whisper，输出 `transcript.json`（**词级时间戳**）以及 srt/vtt。这一步是把"音频"变成"可被构图引用的时间数据"。

**④ 写构图。** 每个场景一个 HTML 片段，元素上挂 `data-start` / `data-duration`，动画写在一个 paused 的 GSAP timeline 里。

**⑤ 检查。** 三个层次：
- `lint` —— 静态契约检查（属性是否合法、有没有注册时间轴、video 有没有声明 muted）；
- `check` —— 打开浏览器跑运行时检查：版式、运动、**对比度**；
- `snapshot --at 0,2,5` —— 在指定时刻抽帧，人眼看。

**⑥ 逐帧渲染。** `npx hyperframes render --fps 60 --workers N`。这一段的耗时占了全流程 90% 以上，第八节有实测。

**⑦ 编码混音。** FFmpeg，默认 `--quality looks` 即 **CRF 16**；音频另有 `normalize-audio --target` 做响度归一。

### 这一步顺序，就是整件事的诀窍

注意 ②③ 在 ④ 前面。**先有音频，才有时间轴；先有时间轴，才写构图。**

不是"先做好画面，再配旁白，再手工对齐"。而是：

```
旁白时长 → 词级时间戳 → 每个元素的 data-start 挂在某个词上 → 画面自动跟着口播走
```

后果很直接：**全片没有一句旁白和画面对不上，因为对齐是编译期保证的，不是手工调的。** 你回看这四部片子，会发现画面切走的那一刻，几乎总是旁白说完某个短语的那一刻——这不是剪辑手感，是数据结构。

HyperFrames 甚至支持相对时间：`data-start="intro + 0.5"`，意思是"intro 这个片段结束后 0.5 秒"。**构图可以声明"我跟着上一段走"，而不必写死绝对秒数。** 这是纯手工剪辑做不到的——你改一句旁白，后面整条时间轴会自动顺延。

### 补一句：这 119 个构图是谁写的

这是个绕不开的问题。第五节测出 EP.09 有 119 个构图，按我复现的密度外推，一部片子是 1.5–4 万行代码（C 级推断）。一个人手写这么多，工期是以月计的。

HyperFrames 的答案在它的口号最后半句："Built for agents"。

它随包带一套 **skills**——不是插件，是**给 AI 编程助手的规则文档**：

```bash
npx hyperframes skills              # 列出全部已发布 skill
npx hyperframes skills update       # 安装/刷新核心 skill
npx hyperframes skills update <name> # 装单个按需 skill
npx skills add heygen-com/hyperframes # 或者从仓库直接装
```

这些 skill 里写的是什么？就是这篇文章前四节讲的那些东西：`data-*` 契约、时间轴必须 `paused: true` 并注册到 `window.__timelines`、确定性三条禁令、13 类动画技法、缓动搭配纪律、常见 lint 错误怎么改。

**换句话说：作者把"怎么写出合法构图"这件事，从人的经验变成了可以注入给 agent 的文档。**

于是闭环变成这样：

```
人：这一屏要讲什么（一句话）
 ↓
agent：按 skill 规则写出构图 HTML + timeline
 ↓
lint：静态契约错（属性写错、没注册时间轴、video 没声明 muted）→ 立刻报
 ↓
check：运行时错（版式溢出、对比度不足、运动异常）→ 打开浏览器跑一遍
 ↓
snapshot --at 0,2,5：抽 3 帧，人眼看
 ↓
render：全片
```

这个闭环的关键价值不是"AI 写代码快"，而是**错误在渲染前被抓住**。想想那个代价对比：`lint` 抓一个错要 0.2 秒，`render` 出来才发现要 40 分钟。**所以这套工具真正的设计重心，是把检查前移。**

但边界也很清楚：**agent 能写出合法的构图，写不出"这一屏该讲什么"。** 那个"预填充卡算力、解码卡带宽，所以要用两种芯片"的论证结构，那个"用琥珀和青对撞"的表达选择，那个"最长 50 秒留给推导"的节奏判断——这些不在 skill 里，在写脚本的人脑子里。

**我的推断（C 级）**：这个系列大概是"人定分镜与文案 → agent 写实现 → 人审抽帧"的分工。片中没有出现任何"AI 生成"的痕迹在画面上（除了片头那几秒主动标注的），说明人审这一关是认真的。

## 四、确定性：整个方案的地基

### 为什么必须是确定的

三个硬约束：

1. **74,434 帧，人不可能一帧帧看。** 一部 20 分 41 秒的 60 fps 片子就是这么多帧（实测 `nb_frames`，见第五节）。你唯一能检查的是抽样。
2. **一次渲染要 30–120 分钟。** 如果跑两遍结果不一样，你就无法判断"改这一行到底有没有用"。
3. **改一个数字就要重渲染。** 如果渲染不可复现，你永远不知道变化是来自你的修改，还是来自运行时抖动。

### 官方给的三条禁令

HyperFrames 的 HTML schema 文档里，动画契约写得很短：

> create one finite timeline with `{ paused: true }`; register it on `window.__timelines`; use the same key as `data-composition-id`; **avoid wall-clock state, unseeded randomness, and infinite repeats**.

翻成工程约束：

| 禁止 | 为什么 | 替代方案 |
| --- | --- | --- |
| `Date.now()` / `performance.now()` | 每帧取到的时间都不一样 | 时间由渲染器通过 `seek(t)` 传进来 |
| `Math.random()` | 每次跑都是不同的画面 | 用坐标做种子的确定性 `hash(x, y)` |
| `repeat: -1` | 无限时间轴，总时长不可知 | 明确写死 `duration` |
| 在异步回调里建时间轴 | 注册时可能还没建好 | 建完再注册，或用 `data-no-timeline` 声明"本构图无时间轴" |
| 手动 `video.play()` / 设 `currentTime` | 播放由框架接管 | 用 `data-media-start` 声明偏移 |

最后一条值得单独说：**视频元素也不能自己播。** 框架要能在任意时刻把视频 seek 到任意位置截图，所以播放权必须交给它。这也是为什么片头那几秒 AI 生成镜头能无缝嵌进代码绘制的画面里——在渲染器眼里，视频和 SVG 没有区别，都是"某个时刻的某个状态"。

### 我怎么验证这 60 fps 是真的

这一条是可以被证伪的，所以我做了实验（B 级）。

如果一部片子是 30 fps 渲染、再用补帧算法插到 60 fps，那么必然有一半的帧间隔**恰好等于 0**（原帧和它复制出来的那一帧完全一样）。反过来，如果每一帧都不一样，就说明是真逐帧渲染。

我取 EP.09 第 200–260 秒这 60 秒，用 `tblend=difference` 逐帧做差，输出 3,599 个相邻帧的平均绝对差：

| 统计量 | 值 |
| --- | --- |
| 样本数 | 3,599 |
| 最小值 | 0.0002（不是 0） |
| p10 / 中位数 / p90 | 0.0265 / 0.2411 / 1.1637 |
| 最大值 | 9.7771 |
| **精确等于 0 的帧** | **0 个** |
| 近静止（< 0.005） | 49 帧，占 1.4% |
| 剧烈变化（> 0.5） | 1,091 帧，占 30.3% |

![60 秒里 3,599 个帧间隔，没有一个是 0](images/fig03_motion.png)

![差分分布是连续的，没有在 0 处堆积](images/fig04_hist.png)

**结论：0 个精确零值，分布是连续的对数正态形状，没有在 0 处堆积。这 60 fps 是真逐帧渲染出来的。**

顺带得到两个副产品：

- **1.4% 的近静止帧**说明画面几乎从不停下来；
- **30.3% 的帧有剧烈变化**说明"一直在动"不是靠背景微动凑数，是真的在频繁重排。

## 五、它的视觉语法：从 107 帧里量出来的

这一节全部是 B 级：我把四部片的关键帧拉出来，用像素测量反推设计令牌。

![实测色板：两个有语义的色相，其余全是灰阶](images/fig06_palette.png)

### 设计令牌实测表

| 项 | 实测值 | 怎么量的 |
| --- | --- | --- |
| 画幅 | 1920 × 1080 | `ffprobe` |
| 帧率 | **60 fps**，严格 CFR | `r_frame_rate=60/1`，且 `nb_frames` 与 `时长×60` 完全吻合 |
| 编码 | H.264 High，yuv420p，bt709，tv range | `ffprobe` |
| 码率 | 1.43 – 1.90 Mbps | `ffprobe` |
| 底色 | `#030405` – `#030708` | 取画面空白区众数 |
| 取景框内缩 | **36 px** | 找四角括号竖臂的像素坐标 |
| 取景框臂长 / 描边 | 35 px / 2 px | 同上，沿行/列扫描 |
| 顶部进度条 | **4 px 通栏**，宽度 = 已播 / 全长 | 扫描 y=0..3 的亮像素范围 |
| 章节号位置 | 左上，内缩 + 28 px | 像素定位 |
| 时间码 | 右下，`TC MM:SS:FF` | 帧内文字 |
| 安全边距 | 左右 1.7%，上 2.2%，下 **5.9%** | 内容包围盒 vs 画幅 |
| 语义色 | 琥珀 `#FF8A3D` / 青 `#4FD1E8`，**仅此两色** | 高饱和像素聚类 |
| 烧录字幕 | 固定位置，约 40 px 字高 | 帧内文字 |

![取景框、进度条、算式条、时间码的位置与尺寸](images/fig07_chrome.png)

### 三个从数字里读出来的判断

**（1）两个色相，就是整条片子的全部论点。**

琥珀＝算力 / 热 / 预填充；青＝带宽 / 冷 / 解码。全片没有第三个语义色。红只在"出错了"出现，绿只在"省下来了"出现。

这不是审美选择，是**让颜色替观众承担一部分阅读理解**。EP.09 讲"预填充卡算力、解码卡带宽"，观众其实不需要记住这两个词——只要看到橙色块和青色块对撞，就知道"这两件事是相反的"。到了 EP.04 讲 CPO，橙色仍然是"热/功耗"，青色仍然是"光/带宽"，语义完全复用。**跨集复用同一套色彩语义，是这个系列能连看的关键。**

**（2）时间码末位跑到 59，说明是 60 fps；而且是全局时间码。**

我抽到的帧里，时间码出现过 `TC 03:39:06`，也出现过 `TC 00:22:06`——中间位是分秒，末位是帧号。末位能到 59，反证 60 fps（A+B 级交叉验证）。

更重要的是：**这是全局时间码，不是每章从 0 开始。** 说明整片在渲染器眼里是一条连续时间轴，不是 119 个独立片段拼起来。这和"一个 `data-duration` 覆盖全片"的架构一致。

**（3）顶部进度条宽度 = 已播 / 全长，是"全局时间轴"的第二个证据。**

我在 `TC 03:39` 那一帧量了进度条：343 px / 1920 px = **17.9%**。而 219.1 s / 1240.6 s = **17.7%**。误差在进度条圆角以内。**进度条是算出来的，不是画上去的。**

这条小细节其实很说明问题：它是一个纯 CSS 的 `width: calc(t / T * 100%)`，但因为 `t` 是全局的，它顺手变成了一个精准的播放进度指示器。手工剪辑要额外做一层，这里是免费的。

**（4）设计系统在这四集里演化过，不是一开始就定好的。**

对比 EP.04 和 EP.09 的角标布局：EP.04 没有底部算式条，时间码位置也不同；EP.09 多了一条常驻的底部算式条（`H·100 · 989 TFLOPS ÷ 3.35 TB/s ≈ 300`），时间码挪到右下角贴着取景框。

这说明设计系统是**逐步长出来的**，不是先做完一套规范再开工。对想抄的人来说这是个好消息：**你不需要一次设计对，你可以先做一集，再改。**

### 节奏：119 个构图，中位 7 秒换一次

我把 EP.09 全长 1,241 秒按 1 fps 采样成 1,241 张缩略图，算相邻差异，取 ≥ p85 的局部峰值（最小间隔 3 秒）作为"构图级切换"：

| 指标 | 值 |
| --- | --- |
| 构图级切换 | **119 个** |
| 平均每个构图 | 10.4 秒 |
| 中位间隔 | **7 秒** |
| 最短 / 最长间隔 | 3 秒 / 50 秒 |
| 硬切（scene score > 0.10） | 17 分钟片 28 次；16 分钟片 3 次 |

![1,241 秒里 119 个构图级切换](images/fig05_cadence.png)

三个数字放在一起看，能读出方法论：

- **中位 7 秒**意味着观众平均每 7 秒就得到一个新画面。这个节奏比大多数技术讲解视频快，但比"每 2 秒一闪"的短视频慢——它刚好够你把一句话听完，又不至于盯着一个静止画面等。
- **最长 50 秒**的那一段，是留给推导过程慢慢走完的。节奏不是均匀的，是**跟着论证的密度走的**。
- **几乎没有硬切**（17 分钟 28 次，平均 36 秒才一次）。构图之间靠连续过渡交接：上一套元素加速上移 + 模糊退出，下一套从反方向减速进入。这就是为什么它"看着特别顺"——**没有一处是"啪"地断掉的**。

### "一直在动"的机制：底噪

最关键的一条：**全片 0% 的帧是完全静止的。**

哪怕画面主体不动，底层也一直在动：一层 120 px 网格以每帧 0.1 px 的速度极慢漂移，一层径向光晕以 1.1 rad/s 做呼吸。这两层加起来只贡献了 0.0002–0.005 的平均差，肉眼几乎察觉不到，但它保证了**任何一帧都不是死帧**。

这是一个很便宜、很有效的技巧：渲染成本几乎为零（两个 CSS transform），但观感上"这个画面是活的"。前面测到的 1.4% 近静止帧，就是这些底噪在撑着。

### 解剖一个构图：EP.04 的微环调制器

抽象的"信息密度高"没有说服力，所以我挑一帧拆开数。EP.04 第 03 章讲微环调制器的那一屏，我数出 **14 组独立元素**：

| # | 元素 | 技术 | 是否动 |
| --- | --- | --- | --- |
| 1 | 章节号 `03` + 章节名 | HTML，白底黑字小方块 | 淡入 |
| 2 | 顶部进度条 | CSS `width: t/T` | 连续 |
| 3 | 系列标 `SI·LAB EP.04` | HTML，字距 0.28em | 静态 |
| 4 | `TYPE 2 · MICRORING` 眉标 | HTML，等宽 + 大字距 | 静态 |
| 5 | 主标题「微环调制器 RING」 | HTML，中英混排不同色重 | 逐字入场 |
| 6 | 左上红块「交换芯片 / 几百瓦 / 温度不断变化」 | HTML 卡片 + 辉光 | 呼吸 |
| 7 | 三条热辐射波浪线 | SVG path，`strokeDashoffset` | 流动 |
| 8 | 微环本体（圆环 + 中心 + 号 + 上方电压焊盘） | SVG，多层辉光 | 旋转/脉冲 |
| 9 | 右侧加热线圈（虚线弹簧） | SVG，`stroke-dasharray` 动画 | 收缩/扩张 |
| 10 | 温度计（竖线 + 圆点 + `±0.0 °C`） | SVG + HTML 标签 | 随控制回路变化 |
| 11 | 波导 + 输入 `InP` + 激光器 `λ` + 锥形收窄 + `OUT` | SVG path，青色描边 | 光沿路径走 |
| 12 | 下方 Ge 探测器 + `测量` | SVG 方块 | 静态 |
| 13 | 左下透射谱（坐标轴 + 陷波曲线 + `λ0` / `±0.2` / `±0.4` 标注） | SVG 按公式绘制 | 曲线随 ΔT 平移 |
| 14 | 右侧 `控制电路 CTRL` 面板（加热功率滑杆 + 偏差 `±0.000 nm` + 三行说明） | HTML 面板 + 滑杆动画 | 滑杆移动 |
| 15 | 右下交叉引用卡「EP.03 ▸ 谷歌光路交换」+ 摄像头盯镜子的插图 | HTML 卡片 + 小 SVG | 延迟淡入 |

**15 组元素挤在一个画面里，而且互不遮挡、层级清楚、每一组都在动。**

这就是"效果非常好"的实际来源——不是某一个特效做得多炫，是**一屏能承载的信息量**。而这一屏之所以能承载 15 组元素，是因为每个元素都是独立定位、独立计时的 DOM 节点。换成 PPT 的一页，你放不下也管不住。

顺带一个可以验证的细节：左下那张透射谱是**真的按公式画的**。`ΔT ±0.0 °C → Δλ ±0.00 nm` 的标注和曲线的陷波位置（`λ0`）是对齐的。这种"图不是装饰，是算出来的"做法，在 EP.09 的仪表盘（989 TFLOPS ÷ 3.35 TB/s ≈ 300）和 EP.02 的四笔账里都一致。**它是这套视觉的可信度来源：观众能看出这个图不是随便画的。**

## 六、13 种动画技术，对上具体镜头

HyperFrames 随包带一份动画技法手册（`hyperframes-animation` skill），列了 13 类技术，并给了两条纪律：**一条片子至少用 2–3 种来自不同"物理维度"的技术**（不能全是淡入淡出），**一个构图里至少 3 种缓动**。

我把这 13 类逐条对到了这四部片子的实际画面上：

| # | 技术 | 原理 | 片里在哪 |
| --- | --- | --- | --- |
| 1 | SVG 路径描边 | `strokeDashoffset` 从 `getTotalLength()` 递减 | EP.04 光纤、波导、微环的"画出来"过程 |
| 2 | Canvas 2D 程序化 | GSAP 代理对象 `time: 0→5` + 确定性 `hash(x,y)` | EP.09 的"文本块"：一屏假字，其实是程序生成的条形 |
| 3 | CSS 3D 变换 | 父层 `perspective`，子层 `preserve-3d` | 卡片翻转、面板侧转 |
| 4 | 逐词动态排版 | 由 `transcript.json` 的 `timings[]` 驱动 | EP.09 右侧"写答案"逐字出现 |
| 5 | Lottie | 必须 `autoplay:false, loop:false`，推入 `window.__hfLottie[]` | 图标、指示符 |
| 6 | 视频合成 | 播放权交给框架，用 `data-media-start` 定位 | 片头那几秒 AI 生成镜头 |
| 7 | 打字机 | `tl.call()` 逐字 + `steps(1)` 光标闪烁 | 终端、代码、公式输入 |
| 8 | 可变字体轴 | `font-variation-settings` 动 `wght`/`wdth` | 标题的粗细呼吸 |
| 9 | MotionPathPlugin | 沿 SVG 路径运动 | 光在波导里走、粒子沿链路走 |
| 10 | **速度匹配转场** | `power2.in` 退出 + `power2.out` 进入 + 模糊 | **全片每一次构图交接** |
| 11 | 音频反应 | 预抽 `audio-data.json`，16 频段 @30fps，缩放 ≤5%、辉光 ≤30% | 配乐重音处的脉冲 |
| 12 | `clip-path` 揭示 | 遮罩扩张 | 图表、表格的"揭开" |
| 13 | WebGL 片元着色器 | 有 Canvas 2D 兜底 | 片头、特殊转场 |

两条纪律我逐帧核对过，确实执行了：

- **EP.09 的片头构图**（`TC 00:22`）同时跑了 5 种：逐词排版（右侧文字逐个出现）+ 进度条填充（TTFT 卡）+ 数字滚数（≈32 ms）+ 光标闪烁 + 底噪漂移。
- **EP.04 的微环调制器**那一帧同时有：SVG 描边（波导）+ 曲线绘制（透射谱）+ 滑杆动画（加热功率）+ 虚线弹簧 + 交叉引用卡。而且左下那张透射谱是**真的按公式画的**——`Δλ = ±0.00 nm` 的标注和曲线的陷波位置对得上。

第 10 条（速度匹配转场）值得单独说。它的做法是：**退出用加速曲线（`power2.in`），进入用减速曲线（`power2.out`），两者在交界处速度相等，再加一点运动模糊。** 这样观众的眼睛不会"断"，因为它感受到的是一个连续加速再减速的过程，而不是两次独立的动画。

这解释了第五节那个"几乎没有硬切"的测量结果——**它不是不用转场，是把转场做成了观众察觉不到的形态。**

### 为什么必须是代码，而不是模板

这是整份调研里我最想讲清楚的一点，因为它决定了"能不能抄"。

模板工具（PPT、Canva、AE 模板）的**原子是"页"**：你做好一页，切到下一页。页与页之间只有切换关系。

代码的**原子是"元素 + 时间区间"**：每个元素有自己的 `data-start` 和 `data-duration`，可以独立进出、互相重叠、彼此引用。

这个差别在观感上是决定性的：

| 想做的事 | 模板工具 | 代码 |
| --- | --- | --- |
| 数字在 3.2 s 内从 0 滚到 295 | 要装插件或手 K 帧 | 一行 `Math.round(easeOut(seg(t,4.05,5.15))*295)` |
| 滚数的同时，左边的条从 0 填到 100% | 两个独立动画，容易不同步 | 同一帧算出来，天然同步 |
| 第 7 个构图里的数字和第 3 个构图里的必须一致 | 手工改十几处，必错 | 一个变量，全片引用 |
| 改一句旁白，后面 30 个构图要顺延 | 逐个拖，拖完还要重对 | `data-start="intro + 0.5"`，自动顺延 |
| 这一屏所有元素都慢 0.2 秒 | 全选 + 拖 | 改一个 `t0` 常量 |
| 想确认第 12,000 帧对不对 | 拖时间轴，可能拖不准 | `snapshot --at 200`，精确到帧 |

最后一条特别值得说。**在代码里，"第几帧"是一个可以被寻址的东西。** 你可以写脚本说"把第 200 秒到 260 秒抽 60 帧出来，算一下相邻帧差异"——这就是我第四、五节做的事。在一部 AE 工程里，你没法这么干。

还有一个隐性收益：**可 diff**。这个系列的片子数字很多（989 TFLOPS、3.35 TB/s、295 ops/byte、30 W、9 W……），数字会随公开资料更新而改。如果是代码，一次 commit 就能看到"这一版把 295 改成了 300，涉及 4 个构图"；如果是 AE 工程，你只能靠人肉记忆。

**所以"代码"在这里不是为了炫技，是因为这个内容形态本身要求可寻址、可参数化、可复现。** 换成纯视觉创意的片子，代码反而会更慢。

## 七、我复现了一遍

这一节是查文档查不出来的部分。我把整条管线在本机重写了一遍，只用了两个文件、约 250 行。

### 契约：一个纯函数

整个方案的技术核心小到可以写在一行里：

```js
window.__hf = { duration: 6.0, fps: 30, seek };
```

`seek(t)` 是一个**纯函数**：给它一个时刻，它把页面所有元素的状态设成那一刻该有的样子。不读时钟、不读随机数、不依赖上一次调用。

```js
function seek(t) {
  // 取景框与标签：描边式淡入
  const chrome = easeOut(seg(t, 0.0, 0.5));
  document.querySelectorAll(".br").forEach(b => { b.style.opacity = chrome; });

  // 主标题：逐字入场（每字 55 ms，模拟"逐词排版"）
  spans.forEach((s, i) => {
    const p = easeOut(seg(t, 0.40 + i * 0.055, 0.40 + i * 0.055 + 0.34));
    s.style.opacity = p;
    s.style.transform = `translateY(${(1 - p) * 18}px)`;
  });

  // 构图 A 退场：加速 + 上移 + 模糊，让位给构图 B
  const outA = easeIn(seg(t, 3.60, 3.95));
  el("stageA").style.filter = outA > 0 ? `blur(${outA * 8}px)` : "none";

  // 构图 B：数字表盘滚数
  el("gn").textContent = Math.round(easeOut(seg(t, 4.05, 5.15)) * 295);

  // 顶部进度条 = t / T
  el("prog").style.width = (t / DUR * 100) + "%";

  // 底噪：极慢网格漂移，保证任何一帧都不是死帧
  el("grid").style.transform = `translate(${-t * 6}px,${-t * 3}px)`;
  el("glow").style.opacity = 0.75 + 0.25 * Math.sin(t * 1.1);
}
```

注意 `seg(t, t0, t1)` 这个辅助函数——它把"从 t0 到 t1 的进度"归一化到 0–1。整个 6 秒构图就是十几个 `seg` 叠加不同的缓动。**没有任何一处依赖"上一帧是什么状态"**，所以渲染器可以任意顺序、任意次数地跳帧，结果都一样。

### 渲染器：40 行

```js
const { duration, fps } = await p.evaluate(() => window.__hf);
const total = Math.round(duration * fps);
for (let i = 0; i < total; i++) {
  await p.evaluate(tt => window.__hf.seek(tt), i / fps);   // 精确 seek
  await p.screenshot({ path: `frames/f${String(i).padStart(4, "0")}.png` });
}
// 之后交给 FFmpeg
```

```

```

## 八、成本：诚实版

### 先看规格

![四部正片的规格对比，右下是同期会议录像作对照](images/fig02_spec.png)

四部正片规格完全一致：1920×1080、**60 fps**、H.264 High、yuv420p、bt709。码率只有 1.43–1.90 Mbps。

**码率低不是因为画质低。** 大面积纯暗底 + 平涂图形，时间冗余极高，CRF 16 也只能压到 1.4 Mbps 左右。作为对照，同一批下载里那条 OCP 会议录像（25 fps 的 Zoom 录制）码率只有 114 kbps——那才是"画质被压掉"的样子。这条对照也说明：**60 fps + CRF 16 的暗底图形，文件比想象中小得多**，一部 20 分钟的片子只有 300 MB。

### 渲染要多久

我把帧数按 HyperFrames 的 `--workers` 模型分片，在本机实测（B 级）：

![本机实测：PNG vs JPEG，1/4/8 worker](images/fig08_bench.png)

| 配置 | 毫秒 / 帧 | 相对单 worker PNG |
| --- | --- | --- |
| PNG · 1 worker | 97 | 1.00× |
| PNG · 4 worker | 81 | 1.20× |
| PNG · 8 worker | 75 | 1.29× |
| JPEG · 1 worker | 44 | 2.20× |
| JPEG · 4 worker | **25** | **3.88×** |
| JPEG · 8 worker | 23 | 4.22× |

三个观察，每一条都指向不同的决策：

1. **换 JPEG 比加 worker 有效。** PNG 8 worker 仍要 75 ms/帧，JPEG 4 worker 只要 25 ms/帧。
2. **加 worker 边际收益很低。** PNG 从 1 到 8 只快 1.29×，因为瓶颈不在浏览器渲染，而在**截图的编码与 CDP 传输**——那是一段串行的管道，多开 worker 只是在管道口排队。
3. 这也解释了为什么 HyperFrames 把 `--video-frame-format` 默认设为 `auto`（偏 jpg），以及为什么另有两个加速开关：`--experimental-fast-capture`（Chrome 的 draw-element 捕获，约 2×）和 `--page-side-compositing`（页面内合成，约 6×，仅 shader 转场）。

把这些数字套到一部真实片子上——EP.09，1,240.6 秒 × 60 fps = **74,434 帧**：

![一部 20 分钟的片子，本机要渲多久](images/fig09_cost.png)

| 配置 | 逐帧捕获 | FFmpeg 编码 | 合计 |
| --- | --- | --- | --- |
| PNG · 1 worker | 120 分 | 6 分 | **126 分** |
| PNG · 8 worker | 93 分 | 6 分 | 99 分 |
| JPEG · 1 worker | 55 分 | 6 分 | 60 分 |
| JPEG · 4 worker | 31 分 | 6 分 | **37 分** |
| JPEG · 8 worker | 29 分 | 6 分 | 34 分 |

（编码实测 213 fps，74,434 帧约 5.8 分钟。preset medium，CRF 16。）

**所以一部 20 分钟的片子，最省 34 分钟、最费 126 分钟。** 机器时间不是瓶颈——你完全可以睡前挂上，早上拿片子。

### 真正的成本在别处

| 成本项 | 量级 | 依据 |
| --- | --- | --- |
| 机器渲染 | 0.5 – 2 小时 / 部 | B 级实测 |
| 构图数量 | ~119 个 / 部 | B 级实测 |
| 每个构图的代码量 | 100 – 400 行 HTML/SVG/JS | **C 级推断**（按我复现的骨架与片中密度外推） |
| 一部片子的代码总量 | 1.5 – 4 万行 | **C 级推断** |
| 旁白 | 免费（本地 Kokoro） | A 级，官方文档 |

**渲染是免费的，写构图是贵的。** 这是这套方法最反直觉的一点：它把视频制作里最耗时的"渲染/导出/转码"压缩到了接近零，然后把全部成本推到了"想清楚这一屏该画什么"上。

## 九、代价与风险

我不打算只讲优点。这套方法有五个明确的代价：

**（1）没有所见即所得的手感。**

你改一行 CSS，要等 30–120 分钟才知道对不对。所以 `snapshot --at 0,2,5` 抽帧检查是必需品，不是可选项。整个工作流被迫变成"先想清楚，再渲一小段验证，最后全片"——这对有经验的人是加分（强迫你想清楚），对新手是折磨。

**（2）确定性是有代价的。**

不能用 `Date.now()`、不能用随机数、不能用无限循环、不能自己控制视频播放。写惯了 Web 动画的人会一直踩这些坑。而且这些错误**不会在预览时暴露**——`preview` 里跑得好好的，`render` 出来才发现第 12,000 帧抖了一下。

**（3）AI 语音有天花板。**

我测了 EP.02 的语速：**209 汉字/分钟**（3,527 个汉字 / 1,013 秒）。这个速度是有意的——比短视频慢，比有声书略快，刚好让画面跟得上。

更说明问题的是响度：**-14.09 LUFS，真峰值 -1.75 dBTP，LRA 只有 3.10 LU。**

LRA 3.1 LU 是什么概念？真人讲述的 LRA 通常在 5–8 LU（有起伏、有重音、有停顿）。3.1 LU 说明整条音轨被压得非常平——这是 TTS 加上限幅器之后的典型特征。**听感是"稳"，不是"有情绪"。**

还有一条：全片**没有一处 ≥0.35 秒的真静音**（`silencedetect` 在 -45 dB 下检出 0 段），底噪稳定在 -39 dB。这说明配乐是**铺满全长**的底床，旁白压在上面，最后过一道限幅。好处是听觉上从不断档；代价是你永远得不到"说完了，静一下"的那种重量感。

**（4）字体授权要自己理清。**

整片是文字密集的，字体是核心资产。把商用字体渲染成视频分发，授权链条和"网页上用 webfont"不是一回事。这一点 HyperFrames 不管，得自己查。

**（5）审美无法自动化。**

这是最根本的一条。这套工具解决的是"怎么把画面渲出来"，不是"该画什么"。

119 个构图的设计判断——这里该用条形图还是仪表盘、这个数字该滚数还是直接出现、这一屏该留白还是塞满——**全部是人的活**。HyperFrames 的 skills 机制能让 AI 写出合法的构图，但写不出"这一屏该讲什么"。

所以回到你最初的观感："效果和动画都非常好"。好的部分不在渲染器里，在**那 119 个构图的设计**里。渲染器只是让这些设计能被低成本地实现出来。

## 十、如果你要自己做：最小可跑骨架

### 目录

```
my-video/
├── scene.html          # 构图（HTML + CSS + seek 函数）
├── render.mjs          # 渲染器（Puppeteer + FFmpeg）
├── frames/             # 中间帧（可删）
└── out.mp4
```

### 三个必须遵守的约定

1. **画面尺寸写死**：`html, body { width:1920px; height:1080px; overflow:hidden }`
2. **状态是 t 的纯函数**：所有元素样式在 `seek(t)` 里算出来，不读时钟、不读随机数
3. **暴露契约**：`window.__hf = { duration, fps, seek }`

### 命令

```bash
# 环境
node --version          # 需要 >= 22
ffmpeg -version
```

### 三个从这次复现里学到的坑

1. **不要用 `loading="lazy"`。** 无头 Chrome 截图时，视口外的图片 `naturalWidth === 0`，会被误判成"图挂了"。
2. **不要用 CSS `animation`。** 它跟渲染器的 seek 不同步。要么用 GSAP paused timeline，要么像我这个 demo 一样，全部在 `seek(t)` 里算。
3. **PNG 换 JPEG。** 这一条能省 60% 的时间，代价是极端渐变处可能有一点点色带。对暗底图形来说看不出来。

### 如果你只想抄观感，抄这五条

不需要复刻整套管线。这五条是"看起来像"的最小集合，按投入产出比排序：

1. **底色压到 `#04060A`，然后只留两个语义色。** 一个暖（算力/热）、一个冷（带宽/光）。别的颜色一律不要。这一步改完，气质立刻对。
2. **四角取景框，内缩 36 px，臂长 35 px，2 px 描边，颜色 `#3A4757`。** 一个 `::before`/`::after` 加两个 div 就能做。
3. **加底噪。** 一层极淡的网格（120 px，不透明度 0.18）以每帧 0.1 px 漂移，一层径向光晕做 1.1 rad/s 呼吸。**成本几乎为零，但画面立刻"活"了。**
4. **转场用速度匹配。** 退出加速（`power2.in`）+ 上移 26 px + 模糊 8 px，进入用 `power2.out` 反方向。**不要用硬切，也不要只做透明度渐变。**
5. **数字滚数，不要直接出现。** 0 → 目标值，用 `easeOut`，1.1 秒。这是最便宜的高级感。

再加一条可选的：**烧录字幕固定在同一个位置，永远不跳。** 观众的眼睛会自动忽略它，但缺了它整片会显得"空"。
