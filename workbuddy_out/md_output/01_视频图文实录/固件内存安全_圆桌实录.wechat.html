背景　安全启动解决了什么，没解决什么

主持人开宗明义：固件认证与安全启动解决的是"固件从哪来"，而不是"固件内部是否安全"。这一区分是整场讨论的出发点。

中文译文　今天我们要谈的是在固件栈上扩展内存安全。先说个起点：我们确实有固件认证、安全启动、认证启动这些东西——它们真正保证的是，你交给系统的固件来自一个经过认证的版本，你不想运行未经验证的固件。但它并不提供固件内部本身的安全性。尽管我们已经把固件部署了好几代，但因为新语言、新机制不断出现，我们需要重新审视，看看在固件领域、在整个栈上能做什么——不只是我们，可能还有 BMC，以及任何我们写固件的地方，它可以是任何微控制器，对吧？所以我们觉得可以组织一场圆桌，讨论从这里能往哪走。

"today we're going to talk about scaling memory safety across firmware stack. um to kind of start with right we do have a uh firmware authentication secure boot authenticated boot those are really take make sure that the firmware that you're giving to the system it's uh coming from authenticated uh version you don't want to run authenticated firmware but it does not provide the security inside the firmware itself um even though we have deployed the firmware for multiple generations s uh because of new languages and new mechanisms are showing up. We need to kind of revisit and see what we can do in the firmware area across stack not just by us probably even BMC and wherever the we are writing firmware it can be microcontroller anywhere right so we thought we can have a panel and can discuss about what we can do go from here right"

小结　安全启动只保证"来源可信"，不保证"实现无缺陷"。随着新语言与新机制出现，固件层需要重新审视——且范围不止于主机固件，还包括 BMC 与各类微控制器。

一　为什么"现在"要关注固件内存安全

1.1　增量改良已经推不动了

中文译文　就在我走上这个讲台之前，我在想：我们时不时会走到一个点，那时增量式的改动已经推不动指针了，于是我们必须换一种完全不同的方式去思考。固件大概就处在这样一个位置。这也是为什么我们在琢磨那个老掉牙的问题——内存安全。那么，我们怎么解决它？我们必须想得不一样一点。怎么做到？

"every um now and then we get to a point where the incremental changes just don't move the needle and so we have to start thinking about things very differently. So firmware is kind of such place that it is in and um so we which is why we are pondering over the age-old question if you will right memory safety. So how do we how do we solve that? So we have to think a bit uh differently and how do we do that?"

小结　内存安全不是一个新问题，而是"老问题 + 增量手段失效"。Raj 的论断是：继续做局部改良不会改变结果，必须换方法。

1.2　"完美风暴"：三个因素同时到来

中文译文　我们目前在这个问题上正处于一场"完美风暴"之中。因为就在固件相关问题的数量出现尖峰的同时——这些是 AI 发现的。如果你现在还没关注 Mythos，你应该去关注，因为我们通常一年会遇到两波尖峰，那些通常来自我们芯片厂商的朋友们。但最近三个月，我们遇到了第三波尖峰，而这一波是 AI 发现的安全漏洞，其规模与我们传统上从其他地方看到的相当。

同时，这些问题中有 60% 到 70% 是内存问题——Google 的研究表明 60% 到 70% 的安全问题与内存相关。第三件事是，我们有来自欧盟等地的监管要求，它们在说："顺便说一句，如果你有安全问题，你的时间非常有限，你必须披露，而且你修复它的时间非常有限。"所以这些事情恰好在同一时刻汇合到一起。它基本上是在说：如果我们不解决其中一个问题，我们余生就都在做安全缺陷修复了。

而且不只是欧盟，我想美国也一样——他们提出来了，后来撤销了一些，但没错，世界各地的监管要求正在把安全变成产品出货的根本条件，这就是这里"完美风暴"的第三部分。

"We we're currently kind of a perfect storm for this issue as well because at the same time that we have the spike in issues uh in firmware related to um AI discovered. Um if you're not looking at Mythos right now, you should be because we usually get two spikes a year and those come usually from our silicon vendors friends. But now we fin this last three months we've have a third spike and that spike is uh AI discovered security vulnerabilities equal in size to the ones we've traditionally had from other places. At the same time we have 60 and 70% of those issues are memory issues as Google has done studies that show that 60 to 70% of uh security issues are memory related. And the third thing is we've got regulatory requirements from places like the EU which are saying, 'Hey, by the way, if you have a security issue, you've got very limited, you must disclose it and you have very limited time to fix it.' So those things are coming together at the exact same time. And it's basically saying if we got if we don't solve one of these problems, we're going to be we'll be doing security bug fixes for the rest of our lives. >> And it's not just EU, I think it's uh US as well. uh right they came up with it and then they resended some but yes they're >> regulatory requirements from around the world are driving security as a fundamental thing shipping your product and that's that's the part of the perfect storm here of three things"

小结　三重叠加：①AI 发现的漏洞形成"第三波尖峰"（历史上每年两波，均来自芯片厂商）；②其中 60–70% 属内存类问题；③欧盟等地监管要求强制披露与限期修复。结论很直白——不消除这一类缺陷，团队将永远在做安全补丁。

1.3　超大规模运营者的视角：存量才是主战场

中文译文　从整个行业来看——是的，正如 Raj 和 Tim 总结的，我们看到的是一场完美风暴。但这不是什么新问题：编译器安全、编译期构建时的静态检测等等，这些都已经有了。但正如 Raj 强调的，这不是增量式地看，而是退后一步看，看怎么解决它。因为对我们超大规模运营者来说，其中大部分是存量舰队的维持，而不只是未来——因为 Tim 刚强调的所有这些安全修复，都是我们必须去修的挑战；再加上 FedRAMP 要求和关键的时间 SLA，这对我们变得极其关键，而且从人力上是不可能扩展的。

"from the whole industry right yes as you summarized Raja and Tim right uh it's a perfect storm as we are seeing but this is not the new thing to address your question is right it has been happening like compiler safety like compiler level buildtime static detections and all are there but this is like looking at and revisiting like Raj just highlighted is it's not just incremental looking at taking a step back and looking at it how to solve it because majority of this as a hyperscaler uh is the sustaining fleet not just the future because all these security fixes uh Tim just highlighted are the challenges that we have to go fix and with fed ramp requirements and critical timing SLAs and this becomes a very critical part of us and it is not humanly possible to scale."

小结　超大规模运营者的成本结构决定了优先级：不是"未来新平台"，而是"已部署舰队的维持"。在 FedRAMP 要求与关键 SLA 时限下，人工逐个修的方式在规模上不可行。

1.4　为什么固件层比操作系统层更危险

中文译文（Oleg Ilyasov，AMI）　这些安全漏洞有不同种类。如果它们在操作系统层被发现——系统正在运行、发现那里有个漏洞——那只是更新操作系统、希望一切正常的问题。然而，我们越往栈的下面走，如果到了启动固件，在那里发现安全漏洞，那就危险得多，而且要把修复部署到各个系统、各个平台、各个厂商，也困难得多。所以我们真的需要尽可能早地去对抗它，尽可能多地去思考它。

中文译文（Bertrand Achard，Google）　如果我们回到今天的演讲，我们知道我们在谈内存安全——如你所说，它是固件中安全漏洞的一个非常主要的成因。在座很多人对此熟悉，但实际上很多人并不熟悉，他们倾向于忘掉它、忘掉它的存在。它就像在后台，有时只在最开始运行一下，而这使它特别危险：不仅很多人忘了它，而且它极其强大——一个固件漏洞就能彻底攻陷一个系统。所以业界对内存安全、对固件整体安全保持一定的意识是非常好的，因为这样我们才能让整个平台变得更好。

"the security vulnerabilities are different uh kinds uh if if there if they found in the OS level if the system is running and it is found that there is a vulnerability there it's only a matter of updating the OS and hoping that everything is fine whereas so the lower down the stack we go if we go to the boot firmware if the security vulnerability is found there it's a lot more dangerous and it's a lot harder to deploy the fix across the systems across different platforms across different vendors etc. So we really need to fight it as early as we can. We really need to think about it as much as we can."

"if if we go back to the talk today we know we talk about memory safety like you mentioned it's a major major cause of security vulnerabilities and firmware and firmware many people here are familiar with it but actually a lot of people are not they tend to forget it and forget it exists. It's like in the background it runs only at the beginning sometimes and that makes it particularly dangerous because not only a lot of people forget about it but also it's extremely powerful. you can absolutely completely compromise a system with a firmware vulnerability. So that's why it's very good to have some awareness in the industry about memory safety and general security across the firmware because that's how we're going to make the whole platform better."

小结　两个叠加因素：①越往栈底，修复越难——OS 补丁只需更新，固件缺陷要跨平台、跨厂商部署；②固件"只在启动时运行、平时不可见"，因此被系统性忽视，但其权限足以完全攻陷系统。这正是"被忽视的高权限层"。

二　只换语言重编译就够了吗

主持人提出关键追问：是不是选对语言、重编译一次，安全问题就解决了？还是需要做更多？如果只能选一门语言，哪门最好？

2.1　真正的判据是"何时发现"，不是"用哪种语言"

中文译文（Oleg Ilyasov，AMI）　这不是"有没有最好的语言"的问题，而更在于：我们怎么以一种方式解决它，使我们在代码编译之后、在单元已经出货到现场之后、然后它跑出问题之后，才发现它？那时我们再去调试，调试变得非常棘手，过了很多很多个月，我们才意识到固件里存在那个漏洞。

（主持） 有时是很多年。（Oleg） 有时甚至好几年——没错。它可以一直不被注意到。所以我们需要一种方法，能在编译期就检测出这类内存安全问题——那会是最好的情况。而且外面确实有现成方案，但准确回答这个问题：关键不是语言，而是我们想在哪一环产生影响。我们需要的方案是，赶在它浮现之前。

（Oleg 续） 一个办法就是评审、代码同行评审；还有一些启发式的源码分析器可以跑，找出可能存在的问题。但即便修好了，如你所说，也不能保证一年之后另一个模块被开发出来时，不会一次又一次地引入类似问题。而正如 Raj 所说，如果语言本身原生支持这类问题的"根治"，那对我们来说是非常非常有吸引力的路径。所以关键在编译期——这意味着你需要语言层面的支持。

（Tim Lewis，Insyde） 你编译不过它——如果有问题，它就编译不过，就是这样。这正是我们想要的。

"It's not a question of you know having the best language but it's more of the question of how do we how do we solve it in a way that we don't find it after the code has been compiled after the the the unit has been shipped into the field and it then runs into an issue. We then debug and debug becomes hairy and after many many months we realize the vulnerability that exists in the firmware. >> Sometimes many years >> sometimes even years that is correct. It can go unnoticed and u so what we need is a method to be able to detect such issues such memory safety issues uh during compile time. that would be the best case right and we do have solutions out there but uh precisely to answer the question it's not the language it is uh it is where we want to impact right and the solution that we need is um is is to get ahead of when it surfaces"

"One is just a review a peer review of the code and there is some huristic uh source code analyzers that can be executed and find the potential issues that that can be there even if it's fixed as uh as you mentioned it's not a guarantee that a year after that when another model is developed there will be similar problem introduced again and again and again and like Raj mentioned the language if it supports natively the the cure for this kind of thing is very very attractive approach for us. So it's a compile time that means you need to have language support to >> you cannot compile it if it's if it's >> if it has an issue it won't compile period that's what we want"

小结　判据不是"最好的语言"，而是"把发现时点前移到编译期"。人工评审与启发式静态分析都只能覆盖当次，一年后新模块可能重现同类缺陷；语言级保证的价值在于"有问题就编译不过"——这是从"检查"到"不可能写错"的跃迁。

2.2　强制力的价值：让编译器替管理者说话

中文译文（Tim Lewis）　因为没有一个好办法——如果你手下全是这些 BIOS 工程师，我自己也是一样的处境——你总不能跟所有人说：抱歉，你得停下来，这段代码不能出货。而他们说：但我需要写这段代码，它必须能工作。你说：是的，但我希望它既能工作又安全。那么，如果我有一个工具能保证我写出来的东西是安全的，那简直像金子一样。因为现在我得去跟我的工程师们较劲，而他们非常擅长自我欺骗、告诉自己"我的代码是完美的"，但我们知道那并不真。所以，如果能让编译器来说这句话，而不是我来说，也许我和他们的关系还能保住。

中文译文（Sam Mutu，主持）　我把它看成一个工具，但它不是解决方案，对吧？我们有 codeQL 之类的工具，跑一遍，问题被找出来。但 AI 类工具的一个主要问题是，开发者会说"这不适用于我们"，很轻易就写个理由绕过——因为他们可能看不到全貌。而有了强制机制就更容易，我们不需要人去逐项检查。静态分析工具、MISRA、CWE 这些东西，它们在那儿做个粗略检查，但正如我们过去这么多年看到的，它们并不十分有效。

"because there's no good way for if you got all these engineer bias engineers because I'm in the same boat right you got all these bias engineers you're going to tell them sorry you need to stop >> and you can't ship this code and they said but I need to write this code that has to work and they said yes but I want it to work and be safe well if I can have a tool that will guarantee that when I write the it will be safe. That that would be that's like that's like gold because right now I'm I'm having to I'm having to fight my engineers and and and they they are very good at lying to themselves and telling themselves, 'Oh, my code is perfect, but we know it's not true.' So, if I can have the compiler say it instead of me having to say it, maybe my relationship with them will be saved."

"I see this as a tool, but it's not a solution, right? We have tools like the code QQLs and all we run and the issues are found. But one of the major thing right with the uh AI based tools and all is developers makes oh it doesn't apply to us just easily write off right bypasses but because they may not see the entire thing and having this enforcement makes it easier and we don't need monitors to go check each and everything static static analysis tools and mistra and coarities you know they they are there for cursory check but uh you know they they not very effective as we all have seen in the past so many years."

小结　两个层面的洞察：管理上，编译期强制把"人管人"变成"机器管规则"，消解了安全要求与交付压力之间的长期拉锯；技术上，静态分析与合规工具容易被"这次不适用"轻易绕过，只有强制机制才具备不可协商性。

三　指针与 unsafe：如何让风险可审计

主持人追问：即便做到编译期检查，固件里大量使用指针，怎么处理？

3.1　不是消灭不安全代码，而是压缩它的比例

中文译文（Tim Lewis）　显然，这正是某些语言（比如 Rust）试图解决的问题——它们试图让它……不，你不能把它变成非法。它仍然可以有不安全代码，但至少你可以把不安全代码收窄到占总量的一个越来越小的比例。随着这个比例下降，意味着攻击面下降，也就意味着总体上我得到的代码更安全。

所以有些语言会给我们这个优势，我们正在看：Rust 是那条路吗，还是有更好的办法？但我们必须选定一个，因为如果现在不开始，我们永远不会变得更好。

"obviously that's some things like what some languages like rust are trying to solve right they're trying to make it >> elite Not you can't make it illegal. It can still be unsafe code but at least you can narrow down the unsafe code to a smaller and smaller segment of the total percentage and as that percentage goes down it means the attack surface goes down and that means that I'm in general I'm getting safer code."

"So some languages will give us that advantage and we're so we're looking at how do you is Rust the way that does that or is there some better way but we have to choose something because we can't if we don't start now we will never get any better."

小结　Rust 的价值不在于"消灭不安全"，而在于把不安全部分变成可度量的小比例，从而让攻击面随比例下降而收缩。这也解释了为什么"必须现在就选定一条路"——路线可以再调整，但没有起点就永远没有改善。

3.2　显式标注使风险可检索、可追责

中文译文（Tim Lewis）　关于某些语言（比如 Rust），有一点是：你必须显式标注它。你不标，它就不工作。所以这是一个很大的红旗。如果我要做代码评审，第一件事就是去看每一个 unsafe 段，然后问：为什么这里不安全？他们必须向我解释为什么把它留成那样。如果他们不解释——

（主持） 而且作为开发者，你得亲手敲下 unsafe 这个词。（Tim） 是的，你为此负责。你必须理解为什么。为什么——你为什么把前门的锁留着没锁？你必须知道为什么。

中文译文（Sam Mutu）　但从编译器这一侧看，编译器里也有一些强制检查。可是涉及结构布局和更大的编译单元时，编译器的标志会在某处被覆盖掉。所以这不是一件容易审计的事。而显式标注使它更容易被审计——然后那可以成为我们逐条追踪的东西。初期阶段也许就是先达到同样的水平，然后再做监控。所以你大概可以去搜一遍 unsafe、把它弄清楚，建立一个度量并设置触发告警。

"one thing about some languages like Rust you have to mark it explicitly right >> right you can't you can't it will not work unless you mark it explicitly and so that's a big red flag and if I'm going to do a code review first thing I'm going to look for is look at every single unsafe section and go why is it unsafe and they have to then they have to justify to me why they left it that way. They don't. >> And if you're a developer, you have to type unsafe. >> Yes. >> You're responsible for that. You have to understand why. Why is it is it that >> why did you leave the door on your front door unlocked? >> You have to know why."

"But from the compiler side, right? There are some enforcement even in the compiler. But with the structure layouts and larger compos like the compiler flags are overridden somewhere. So it's not something easy to audit >> and this explicitly marking makes it easier auditable >> and then that could be a one we can track one by one right for initial phase it could be yeah just get this same level then monitoring >> so you can probably go and do a search of unsafe and figure out again >> create a metric and trigger."

小结　Rust 的关键设计不是"消除不安全"，而是"强制标注不安全"：`unsafe` 必须显式写出，于是可被检索、计数、设阈值告警，并在代码评审中逐条要求理由。这把一个不可审计的属性（"这段代码安不安全"）转成了可度量的工程指标（"unsafe 占比与清单"）。

四　迁移路径：从新代码开始，逐层推进

4.1　先新代码，再逐层攻

中文译文（Raj Kapoor，AMD）　我相信每一家想为自己解决这个问题的公司，都在琢磨攻击这个问题的最佳路线是什么。现在我们所有的固件——至少主机固件——都是 C 写的，而且代码库很大，不是小代码库。一个方案是把它转成 Rust。这可行吗？值得怀疑。但你必须从某处开始。

那么从哪里开始？在我看来，从新代码开始：你从新代码开始，并且坚决要求用 Rust 写。那么，只做新代码就能保证你没事吗？不能。但至少球滚起来了。然后你开始看你的层次：下一层技术是什么？你一层一层地攻。
