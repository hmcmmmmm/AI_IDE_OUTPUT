## 摘要：一句话与两张表

**一句话**：一次回答其实是两个活——预填充并行读完整段提问，卡在算力上；解码一个字一个字往外写，每一步都要把全部权重重读一遍，卡在显存带宽上；两种活挤在同一批芯片上会互相拖累（一个长文档能让所有人的字突然停住），于是业界把它们拆成两个池子，进而拆到"按层""按模块"，最后连芯片也分成了两种。

**两种性格，正好相反**

| | 预填充 PREFILL | 解码 DECODE |
| --- | --- | --- |
| 干什么 | 一次读完整个提问，算出 KV 缓存 | 一个字一个字写，每步重读全部权重 |
| 卡在什么 | **算力**（带宽闲着） | **显存带宽**（算力闲着） |
| 用户感受 | TTFT：多久看到第一个字 | TPOT：后面的字吐得多快 |
| 片中的实例值 | 3.00 s（冷开场）／0.40 s（演示） | 32 ms（冷开场）／28 ms（演示） |
| 机器利用率 | 算力 100% 忙 | 算力仅约 2% 忙、带宽 100% 满 |

**三种拆法（这是全片的骨架，也是本文第五节要理清的部分）**

| 拆法 | 怎么拆 | 代表 |
| --- | --- | --- |
| 按阶段 | 预填充池 / 解码池，中间传 KV 缓存 | DistServe、Splitwise、Mooncake、DeepSeek、Dynamo、vLLM、SGLang |
| 按层 | 同一层的不同计算交给不同芯片，逐层协同 | Groq 3 LPX + Vera Rubin NVL72（GPU 算注意力、LPU 算专家） |
| 按模块 | 注意力与 FFN/专家分到不同池子 | MegaScale-Infer；片尾"解码·注意力池 → 解码·专家池" |

## 一、逐段解读

### 1.1 开场：同一个问题，两种体验

![开场：读问题 每个字 TTFT 3.00 秒 / 写答案 之后每个字 TPOT 32 毫秒，中间一道裂痕](images/01_coldopen.jpg)

片子没有从架构讲起，而是把屏幕劈成两半：左边"读问题"，右边"写答案"。

- **读问题**：你贴进去一份合同、一段代码、一整个仓库，它要先读完——计时器显示 **3.00 秒**，标着"每一个字（TTFT）"；
- **写答案**：它开始一个字一个字往外写——**32 ms**，标着"之后每个字（TPOT）"。

字幕给了一句很轻、但正是全片论点的收尾：**"芯片公司已经开始为它们分别造芯片了。"**

### 1.2 两个时钟：TTFT 与 TPOT

![两步 → 两种体验：TTFT 首字时间 0.40 s，TPOT 字间隔 28 ms，是两条独立的"道"](images/04_twoclocks.jpg)

视频把用户感受量化成两个互不相干的指标：

- **TTFT**（Time To First Token，首字时间）：从发出请求到看见第一个字。演示值 **0.40 s**；
- **TPOT**（Time Per Output Token，字间隔）：第一个字之后，后面的字吐得多快。演示值 **28 ms**（约 36 字/秒）。

**为什么必须分成两个指标**：因为它们由两步分别决定，而且可以独立恶化。后面 1.7 那个"长文档拖住所有人"的例子，恶化的正是 TTFT——用户盯着空白屏等 4 秒，而 TPOT 一点没变。

### 1.3 车间：模具、仓库、叉车

![模具运来一次，能冲压几个？仓库=显存、叉车=显存带宽、工人=计算单元、模具=参数](images/05_workshop.jpg)

全片最重要的一次比喻，值得完整复述：

- **模具** = 模型参数（一次冲压要用到的那套形状）；
- **仓库** = 显存（HBM），放模具的地方；
- **叉车** = 显存带宽，把模具从仓库运到车间；
- **工人** = 计算单元（SM），拿到模具才能冲压。

于是问题变成一句话：**一套模具运来一次，能冲压几个？**

- 冲压 **2000 次** → 运模具的时间可以忽略，瓶颈是工人手快不快 = **算力**；
- 冲压 **1 次** → 运模具的时间占满，瓶颈是叉车快不快 = **带宽**。

这个比喻之所以好用，是因为它把"算术强度"这件抽象的事变成了"运输 vs 加工"的比值。

### 1.4 每字节 1 次，而机器要 300 次

![解码的算术强度：1 个参数 16 位 = 2 字节，每字 2 次运算 → 1 次运算/字节；而机器需要约 300](images/06_opsperbyte.jpg)

视频把解码的算术强度算到最细：

```
1 个参数，16 位 = 2 字节
每读 1 个字：× 乘法 + 加法 = 2 次运算
2 次运算 ÷ 2 字节 = 1 次运算 / 字节
```

也就是说，**解码时每从显存搬 1 字节，只做 1 次运算**（批大小为 1 时）。而 H100 要"喂饱"自己需要约 **300 次运算/字节**（`990 TFLOPS ÷ 3.35 TB/s ≈ 296`，见账一）。

中间差了 300 倍——这 300 倍的差距，就是"解码时算力闲着"的全部原因。填平它只有一个办法：**批处理**。同一套模具运来一次，给 300 个人各冲一下。

### 1.5 两种性格

![预填充：模具来一次冲压 2000 次，取决于算力，工人 100% 忙、多的时间在等](images/07_prefill.jpg)

预填充把整段提问一次喂进去，每个权重被用到几百上千次——**取决于算力**。片中的仪表：算力 **100% 忙**，带宽只用了一小部分，"多的时间在等"。

![解码：模具来一次只冲压 1 次，取决于显存带宽，算力只有 2% 在忙](images/08_decode.jpg)

解码每一步只出一个字，全部权重必须重读一遍——**取决于显存带宽**。片中的仪表反过来：带宽 **100% 满**，算力只有 **2%** 在忙。

![两步的性格，正好相反：预填充卡在算力（带宽闲），解码卡在带宽（算力闲）](images/10_halfpower.jpg)

这一屏是全片的概念核心，一句话总结：**同一个模型，两步的瓶颈正好互补。**

互补到什么程度？视频引了微软 Splitwise 的实验：**把解码用 GPU 的功耗上限砍掉 50%，速度几乎不变**。原因很直白——那台机器本来就只有 2% 的算力在干活，降功耗降的是它用不到的那部分。

### 1.6 批的上限：显存

![显存装不下更大的批：8 卡 × 80 GB = 640 GB，KV 缓存那期已经算过](images/09_batching.jpg)

既然填平 300 倍差距靠批处理，那批能开多大？答案是**显存**：8 张 H100 共 **640 GB**，减去权重，剩下的全给 KV 缓存。

这条约束很硬，而且和上下文长度直接冲突：上下文越长，每个请求占的缓存越多，能同时服务的请求越少。账二会把这条算到底——**在 1 万字上下文下，640 GB 只够把批开到 150 左右，也就是算术强度只到 150，仍只有 300 的一半**。所以"解码算力闲着"不是工程没做好，是容量决定的。

### 1.7 挤在一起：一个长文档拖住所有人

![挤在一起：32 个用户、8×H100·70B、算力占用 99%，新用户的首字时间从 0.4 s 变成 4.0 s](images/11_stall.jpg)

前面的分析都是"一步单独跑"。真实系统里两步混跑，问题立刻出现：

屏幕上是 32 个用户的请求在跑，算力占用 **99%**。这时来了一个新用户，贴了一份长文档——他的预填充要插进来。结果：**他自己的首字时间从 0.4 s 变成 4.0 s**，同时**已经在写答案的 32 个人，字突然停住了**。

字幕说得很直白："现在突然停顿了平时十倍左右的时间。"

这是全片最容易被忽略、但对运营最致命的一点：**混跑时，一个人的长输入会变成所有人的延迟抖动**。它不体现在平均吞吐上，体现在 P99 的 TPOT 上。

### 1.8 只能选一种切法，于是有了切块

![两步想要的配置不一样：预填充侧更适合一种切法，解码侧更适合另一种，但一套系统只能选一种](images/13_diffsetup.jpg)

视频接着指出更深一层的矛盾：**两步想要的最优并行配置不一样**。屏幕给了一组对比——预填充侧更适合"窄而深"的切法（图中记作 32⁺ × 9 卡），解码侧更适合"宽而浅"的切法（144 × 2 卡）。但一套系统**只能选一种切法**，另一部只好将就。

（这两个数字的具体含义视频没有展开，此处按画面记录，不作推断。）

![折中：把长问题切成小块（chunked prefill，Sarathi-Serve），矛盾摊薄了，但还在](images/14_chunked.jpg)

折中方案叫**切块预填充**（chunked prefill，Sarathi-Serve）：把长文档切成小块，一块一块地读，每读完一块就让解码组吐几个字。屏幕上的对比很形象——"不切"是一口气读完，所有人都等；"切块"是读到一块给一片。

但视频点出了它的天花板：**矛盾摊薄了，但还在**。因为配置仍然只能选一种。

### 1.9 干脆分开

![一组读问题、一组写答案：预填充池把 KV 缓存经网络送进解码池](images/15_split.jpg)

解法就是把两步拆到两组芯片上：**预填充池**只负责读、算完把 KV 缓存通过网络送过去；**解码池**只负责写，一个字一个字地吐。

拆开之后，两个指标各归各家：预填充组只影响 **TTFT**（图中 0.42 s），解码组只影响 **TPOT**（图中 30 ms）。这才是"拆分"真正买到的东西——**不是吞吐，是解耦**：长文档再长，也不会让别人的字停下来。

### 1.10 从论文到主流

![Splitwise：解码不一定要用最新的卡，H100 与 A100 混用在同样成本下更划算](images/16_distserve.jpg)

视频在这里给了两张论文的结论：

- **DistServe**（OSDI 2024）：在满足 SLO 的前提下，**最多支持 7.4 倍的请求量**；
- **Splitwise**（ISCA 2024）：既然解码卡在带宽、对算力要求低，那就**不必用最新的卡**——H100 做预填充、A100 做解码，在**同样的成本和功耗下**吞吐更好。

第二点是这段里最"反直觉"的一击：拆分的价值不只是快，而是**让每一分钱花在它真正需要的地方**。

![这个思路很快成了主流：2024 论文（DistServe/Splitwise）→ 2025.03 Dynamo 开源 → 2025 年底几乎都支持](images/17_mainstream.jpg)

时间线把"论文 → 工程"的过程压在一屏里：

| 时间 | 事件 |
| --- | --- |
| 2024 | DistServe、Splitwise 两篇论文 |
| 2025.03 | 英伟达 **Dynamo** 开源（"拆分 = 核心功能"） |
| 2025 年底 | Mooncake（月之暗面·Kimi）、DeepSeek 自家推理系统、vLLM、SGLang **几乎都支持** |

从论文到"几乎所有框架都支持"，用了不到两年。这个速度本身就说明：**拆分的收益不是学术上的漂亮，而是账面上的划算**。

### 1.11 搬缓存：3.2 GB 与 65 ms

拆开之后立刻多出一笔新开销：**KV 缓存要在两组芯片之间搬**。视频先问两个问题：搬多少？搬多久？

![要搬多少：Llama 3 70B 每个字 320 KB，× 1 万字 = 3.2 GB，用一条 400G 网络连接来传](images/18_kvmove.jpg)

**搬多少**：Llama 3 70B，每个字（token）的 KV 缓存 **320 KB**，1 万字 → **3.2 GB**。

（这个数可以独立算出来，见账三：`2 × 80 层 × 8 个 KV 头 × 128 维 × 2 字节 = 320 KiB`，与画面完全吻合。）

![这笔账算得过来：读 1 万字 0.4 s（橙），传 3.2 GB 缓存 65 ms（蓝），模型是一层一层算的](images/19_streamlayer.jpg)

**搬多久**：一条 **400G** 的网络连接传 3.2 GB ≈ **65 ms**（账四：3.2 GB ÷ 50 GB/s = 64 ms）。

关键在于最后那句：**模型是一层一层算的**。所以不需要等全部缓存算完再搬——**算完一层就搬一层**（layer-by-layer streaming），传输和解码重叠起来。65 ms 对上 0.4 s 的计算，这笔账才算得过来。

### 1.12 MLA：0.7 GB

![同样一万个字：Llama 3 70B 要 3.2 GB，DeepSeek-V3 的 MLA 只要约 70 KB/字、合计 0.7 GB](images/20_smallcache.jpg)

视频给了一个更省的办法：**换缓存的数据结构，而不是换网络**。

DeepSeek-V3 的 **MLA**（多头潜在注意力）不存完整的 K/V，只存一个压缩过的"摘要"：每个字的缓存从 **320 KB** 降到约 **70 KB**，1 万字 → **0.7 GB**，比 3.2 GB **小了 4 倍多**。

（账五给出 70 KB 的来历：`61 层 × (512 + 64) × 2 字节 ≈ 70 KB`。）

这一屏的逻辑很值得学：**当搬运成为瓶颈时，先问"能不能少搬"，再问"能不能搬快"。** 前者是模型设计（MLA），后者是网络工程（400G/800G）。视频把两条路都摆了。

### 1.13 两边各配多少卡

![比例分错了，好处就被吃掉：预填充池 8 张忙到 100%，解码池 8 张只用到 18%](images/21_poolsizing.jpg)

拆分带来一个新问题：**两边各配多少张卡？**

屏幕上的例子是各 8 张。结果是预填充池忙到 100%，解码池只用到 **18%**——比例分错了，拆分的收益被配置错误吃掉。

视频由此给出一个很实用的判断：**推理系统的配比，取决于业务的长宽比**。

- 长输入、短输出（读长文档、让 AI 总结）→ 预填充重；
- 短输入、长输出（写代码、长对话）→ 解码重。

这也是为什么云厂商不能买"一种标准配置"就完事——**配比是业务参数，不是技术参数**。

### 1.14 芯片也分了：三种能力

![在预填充这一步，HBM 用不满：通用 GPU 的算力/带宽/容量三种能力，两步各取所需，总有很大一部分用不上](images/22_specsheets.jpg)

拆到最后，连芯片也拆了。视频先把一颗 GPU 的能力拆成三维：

| | 算力 | 带宽 | 容量 |
| --- | --- | --- | --- |
| 预填充 | ★★★ | ★★（不是瓶颈） | ★★ |
| 解码 | ★ | ★★★ | ★★★ |

一颗"通用 GPU"要在三个维度上都强，结果就是**两步都有大量能力闲置**——预填充时 HBM 容量闲着，解码时算力闲着。

这句话是全片下半场的引子：**如果两步需要的不是同一张能力表，为什么还要用同一颗芯片？**

### 1.15 华为：一芯双构

![最好的内存，用在刀刃上：昇腾 950PR 配 HiBL 1.0 走预填充/推荐，950DT 配 HiZQ 2.0 走解码/训练](images/23_huawei.jpg)

第一个例子是华为。昇腾 950 系列**同一颗计算 die，配两种内存**：

| | 昇腾 950PR | 昇腾 950DT |
| --- | --- | --- |
| 内存 | **HiBL 1.0**：128 GB / 1.6 TB/s | **HiZQ 2.0**：144 GB / 4 TB/s |
| 用途 | 预填充、推荐业务 | 解码、训练 |
| 时间 | 2026 Q1 | 2026 Q4 |

这条路线和本片论点咬得最紧：**算力一样，只把内存换掉，就得到两种芯片**。因为两步的差别本来就不在算力，在内存。

（带宽差 **4 ÷ 1.6 = 2.5 倍**，容量差 144 ÷ 128 = 1.125 倍——见账六。**这是"用带宽换解码"的教科书式做法。**）

### 1.16 英伟达 Rubin CPX：算力给足

![Rubin CPX：专为长上下文预填充，NVFP4 精度下每秒约 30 千万亿次运算（29 PFLOPS），128 GB GDDR7](images/24_rubincpx.jpg)

第二个例子方向相反：**华为是"换内存"，英伟达是"加算力"。**

Rubin CPX（2025-09 发布）专为**长上下文预填充**：**29 PFLOPS**（NVFP4）、**128 GB GDDR7**。用 GDDR7 而不是 HBM，是因为预填充**不需要高带宽、需要大容量和便宜**——正好和 1.14 那张表对上。

这一步很能说明"拆分"如何改变硬件设计：一旦只服务一步，就可以**在三个维度里公开地偏科**。

### 1.17 Groq：把仓库搬进车间

![解码最缺的是带宽，SRAM 150 TB/s 正好补上：2025.09 英伟达 × Groq，2026.03 GTC 发布 Groq 3 LPU](images/25_groq.jpg)

第三个例子最激进：**解码缺带宽，那就把内存做成 SRAM。**

Groq 3 LPU 不用 HBM，用片上 SRAM，带宽 **150 TB/s**——是 H100 的 3.35 TB/s 的 **45 倍**。片中的比喻就是标题那句：**"仓库搬进车间"**，模具不用叉车运了，伸手就够得着。

代价也很清楚：SRAM 容量小（单芯片几百 MB 量级），装不下大模型，所以要**一个机架 256 颗 LPU 拼起来**（合计 128 GB 片上 SRAM）。

### 1.18 LPU + GPU：按层拆

![分工二·按层拆：GPU 池算注意力，LPU 池算前馈/专家，生成一个字时模型每过一层都要两边协同](images/26_lpu_gpu.jpg)

这是全片技术含量最高的一屏，也是"拆分"的**第二根轴**。

前面讲的拆分都是**按阶段**（预填充 vs 解码）。而 Groq 3 LPX + Vera Rubin NVL72 的玩法是**按层**：

- **GPU 池**：预填充、KV 缓存驻留、解码里的**注意力**部分；
- **LPU 池**：解码里的**前馈/专家**（MoE 的专家层）部分；
- 生成一个字的每一步，模型**每过一层都要在两边协同一次**。

为什么会这样分？因为注意力和 FFN/专家对硬件的偏好不同：注意力要读 KV 缓存（吃带宽、吃容量），FFN/专家要读权重（吃算力、吃 SRAM 带宽）。**分层拆，等于把"两种性格"切到了层内。**

### 1.19 还没结束

![拆分是共识，怎么拆还在摸索：按阶段、按层、按模块三种答案并存，片中还把"CPX 改用 HBM4"标为来源存疑](images/27_notover.jpg)

视频在这里做了一个很诚实的收束：**"拆分"本身已经是共识（打勾），但"硬件怎么拆、拆到哪一层"整个行业还在摸索。**

屏幕上并列了三种答案：按层、按模块（注意力/专家）、按阶段。而且它把自己引用的"2026.09 CPX 改用 HBM4"明确标成**来源存疑**（分析师的供应链报告，英伟达未确认）。

这种标注在科普视频里很少见，值得记一笔。

### 1.20 每个字的成本，与两种用法

![每个字的成本一点点抠下来：预填充池（算力优先、不买 HBM 要密度）→ 解码·注意力池（显存带宽优先）→ 解码·专家池（容量优先）](images/28_pipeline.jpg)

把前面所有拆分串起来，得到一条**流水线**，每一段都按自己最在乎的指标配硬件：

| 段 | 优先 | 硬件取向 |
| --- | --- | --- |
| 预填充池 | 算力 | 不买 HBM，要密度 |
| 解码·注意力池 | 显存带宽 | 买贵一倍的芯片 |
| 解码·专家池 | 容量 | 更便宜、容量更大 |

字幕的总结是：**"每个字的成本，就是这样一点点抠下来的。"**

![哪边涨得快：推理模型要一次读完代码仓库，答案又要越写越长，两边的配比取决于业务](images/30_usage.jpg)

而配比取决于**人怎么用 AI**：如果用户习惯一次贴进整个代码仓库（长输入），预填充就重；如果答案越写越长、还带思维链（长输出），解码就重。**同一套硬件，不同的用法，最优配比不同。**

![速度 ⇄ 价格：马上要就付原价，不着急就打五折——同一组芯片的两种用法](images/31_batchapi.jpg)

最后一屏把这件事推到商业层：**"速度 ⇄ 价格"**。急着要，付原价；不着急，走批处理，**五折**。

这句话的技术含义是：**离线批处理可以把延迟预算全部换成吞吐**（大批、大块预填充、不在乎 TPOT），于是同一组芯片能卖出两种价钱。这也是为什么"拆分"最后不只改变了硬件，还改变了**产品形态**。

## 三、六笔账

### 账一：300 ops/byte 是怎么来的

```
990 TFLOPS ÷ 3.35 TB/s = 295.5 次运算 / 字节 ≈ 300
```

这叫**机器平衡点**（ridge point）：算术强度低于它，芯片就在等内存；高于它，就在等算力。

### 账二：解码能到多少？为什么"砍一半电也不慢"

解码每步要为**每个序列**读一遍全部权重，所以：

```
算术强度 ≈ 批大小 × 1（次运算/字节）
```

要追上 295，批得开到 **295** 左右。那能不能开这么大？看显存：

```
8 × H100 = 640 GB
70B 模型 FP16 权重 ≈ 140 GB
留给 KV 缓存 ≈ 500 GB
1 万字上下文的每个请求 = 3.2 GB
→ 最多约 156 个并发请求
→ 算术强度 ≈ 156，仍只有 295 的一半
```

三个独立来源在这里对上了：

1. 账一算出的门槛 295；
2. 1.6 的显存 640 GB；
3. 1.5 引的"解码功耗砍 50% 速度不变"。

**50% 这个数字不是巧合**——在 1 万字上下文下，显存最多只允许把算术强度推到门槛的一半，所以解码机有一半的算力注定闲着，砍掉一半功耗自然不掉速。

（注意：上下文越短，同样显存能塞下的请求越多，算术强度越高，解码就越接近算力瓶颈。**"解码一定吃带宽"是有前提的**——前提是上下文够长或批够小。这也是 1.13 说"配比取决于业务长宽比"的物理原因。）

### 账三：320 KB/字 的来历

Llama 3 70B 的 KV 缓存，每个 token、每层存 K 和 V 各一份：

```
2（K+V） × 80 层 × 8 个 KV 头 × 128 维 × 2 字节（FP16）
= 327,680 字节 = 320 KiB
```

× 10,000 字 = **3.2 GB**。与画面完全一致。

顺带解释一个容易误解的点：70B 有 64 个注意力头，但 **KV 头只有 8 个**（GQA，分组查询注意力）。**如果按 64 个头存，缓存会大 8 倍，到 25 GB**——GQA 本身就是一次"少搬"的设计，比 MLA 早了好几年。

### 账四：3.2 GB 传多久

```
400 Gbps = 50 GB/s
3.2 GB ÷ 50 GB/s = 0.064 s = 64 ms
```

视频写 65 ms，一致。

再对照 1.11 的 0.4 s 预填充：**传输只占计算的 16%**，而且可以逐层重叠。这就是"这笔账算得过来"的算术依据。

如果换 800G（100 GB/s），降到 32 ms；如果换 MLA（0.7 GB），同样 400G 只要 14 ms。**两条路都能把传输压到计算的 5% 以内。**

### 账五：70 KB/字 的来历

DeepSeek-V3 的 MLA 不存完整 K/V，只存压缩后的潜在向量 + 位置编码：

```
61 层 × (512 潜在维 + 64 RoPE 维) × 2 字节 ≈ 70,272 字节 ≈ 70 KB
```

× 10,000 字 ≈ **0.7 GB**。与画面一致（320 ÷ 70 ≈ 4.6 倍）。

### 账六：950PR 与 950DT 差在哪

```
带宽：4.0 ÷ 1.6 = 2.5 倍
容量：144 ÷ 128 = 1.125 倍
```

**容量几乎没变，带宽差 2.5 倍。** 这正好对应两步的差别：预填充要的是"算得快"，解码要的是"搬得快"。华为没有做两颗不同的计算 die，只换了内存子系统——这是对"两步的差别不在算力、在内存"最直接的产业验证。

## 五、把"拆分"拆成三根轴

这是这份笔记最想理清的一件事：**视频里的"拆分"其实是三件不同的事**，混在一起讲容易让人以为是一条演进路线（先按阶段、再按层、最后按模块），实际上它们是**三个正交的选择**，可以叠加，也可以只选一个。

| 轴 | 切在哪 | 中间要传什么 | 优化什么 | 代价 | 代表 |
| --- | --- | --- | --- | --- | --- |
| **按阶段** | 预填充 / 解码 | **KV 缓存**（3.2 GB / 万字） | 消除两步互相干扰；各配各的卡 | 网络带宽、池子配比 | DistServe、Splitwise、Mooncake、Dynamo |
| **按层** | 同一层内，注意力 / 前馈 | **激活值**（每层一次同步） | 让每层用最合适的存储（SRAM vs HBM） | 层间同步延迟，要求极低抖动 | Groq 3 LPX + NVL72 |
| **按模块** | 注意力 / FFN·专家 | 激活值（按模块） | 专家并行、MoE 的稀疏性 | 调度复杂度、负载不均 | MegaScale-Infer；片尾"注意力池 → 专家池" |

三根轴的**成本结构完全不同**，这是理解它们为什么并存的关键：

- **按阶段**的代价是**一次性搬一大块**（KV 缓存，GB 级），但对网络只要求带宽，不要求低延迟——所以能用普通以太网/IB，能逐层重叠。
- **按层**的代价是**每层同步一次**（一个 token 要过几十层，就是几十次同步），对**延迟抖动**极其敏感。这也解释了 Groq 为什么要做确定性流水线——**它的商业模型建立在"零抖动"上**。
- **按模块**的代价在**调度**：MoE 的专家负载天然不均，切完要解决"某些专家池排队、某些闲着"。

**为什么视频把它们讲成一条线？** 因为从叙事上，"拆得越来越细"确实是一条线（阶段 → 层 → 模块），而且时间上也大致如此（2024 论文 → 2025 框架 → 2026 芯片）。但从工程上，它们是**三个可以独立开关的选项**：

> 一个系统完全可以只做按阶段拆分（今天的 vLLM/SGLang 默认），不做按层也不做按模块；也可以只做按模块（MegaScale-Infer 的思路），不拆阶段。

**这条区分有实际用处**：当你听到"我们做了 disaggregation"时，第一句该问的不是"效果如何"，而是**"你拆的是哪根轴、中间传的是什么"**。传 KV 缓存和传激活值，是完全不同的两个工程问题。

## 六、三个薄弱点

**第一，"每字节 1 次运算"这个推导只在批=1 时成立，但片子没把前提说透。**

1.4 那段把解码的算术强度算成 1 op/byte，然后拿它和 300 比，得出"差 300 倍"。这个对比很震撼，但它是**最坏情况**。真实部署里批总在几十到几百之间，算术强度是"批大小"这个数，不是 1。

结果就是：**"解码算力只用了 2%"这个数字，只在批很小的时候成立**。视频后面用"砍一半电不掉速"来佐证，逻辑是对的，但中间那一步（为什么批开不大）直到 1.6 才补上，且没有把两者显式连起来。

我在账二里补上了这条链——**它其实是个很漂亮的闭环（门槛 295 / 容量 156 / 功耗 50%），但片子把它留成了三个孤立的数字。**

**第二，"按层拆"被当成"更细的按阶段拆"，其实它的成本结构完全不同。**

见第五节。按阶段拆传的是 KV 缓存（一次搬一大块，容忍延迟）；按层拆传的是激活值（每层同步一次，对抖动零容忍）。**后者的工程难度高一个量级**，而视频把它们并列成"拆分的第一种、第二种"，容易让人低估 LPU 那条路的门槛。

**第三，全片的成本账只算到"每个字的成本"，没算"每套系统的成本"。**

1.20 那条流水线把每个字的成本一段段抠下来，但它没有回答一个运营者最关心的问题：**拆成三个池子之后，总拥有成本是升还是降？**

拆分带来的隐性成本至少有四项，片子里一项都没量化：

1. 池子之间要网络（400G/800G 交换机的钱）；
2. 配比错了收益被吃掉（1.13 自己举了 18% 的例子）；
3. 三个池子的故障域变多，可用性管理更复杂；
4. 预填充池的算力是按峰值配的，低谷时闲置。

视频最后用"速度⇄价格"（批处理五折）来回答商业问题，这确实是一条路——**用离线流量填平预填充池的波谷**。但它是一句口号，不是一个模型。

## 七、术语表

| 术语 | 含义 |
| --- | --- |
| 预填充（Prefill） | 一次并行读完整段输入、算出 KV 缓存，算力密集 |
| 解码（Decode） | 逐 token 生成，每步重读全部权重，带宽密集 |
| TTFT | Time To First Token，首字时间，由预填充决定 |
| TPOT | Time Per Output Token，字间隔，由解码决定 |
| 算术强度（arithmetic intensity） | 每搬 1 字节做多少次运算；与机器平衡点比较决定瓶颈 |
| 机器平衡点（ridge point） | 算力 ÷ 带宽，H100 约 295 ops/byte |
| KV 缓存 | 已算过的键值对，避免重复计算；大小随上下文线性增长 |
| GQA | 分组查询注意力，多个 Q 头共享一组 KV 头，直接缩小 KV 缓存 |
| MLA | 多头潜在注意力，把 K/V 压成低维潜在向量，DeepSeek-V3 采用 |
| 连续批处理（continuous batching） | 请求随到随进，不必等整批结束 |
| 切块预填充（chunked prefill） | 把长输入切块与解码交错，摊薄阻塞（Sarathi-Serve） |
| 拆分（disaggregation） | 把预填充与解码分到不同硬件池，中间传 KV 缓存 |
| SLO | 服务等级目标，如 P99 TTFT < 1 s |
| MoE | 混合专家，每 token 只激活部分专家，天然稀疏 |
| SRAM | 片上静态存储，带宽极高但容量小、成本高 |
| LPU | Groq 的确定性流水线推理芯片，用大容量 SRAM 替代 HBM |
