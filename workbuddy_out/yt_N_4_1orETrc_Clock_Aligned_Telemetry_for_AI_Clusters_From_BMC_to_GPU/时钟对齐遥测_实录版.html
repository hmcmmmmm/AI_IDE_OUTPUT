小结　六条通道：GPU、Host、BMC、Placement、Network，加上 Time 本身。关键洞见是把"时间"当作第六条证据通道而非背景参数——只有时间自身的状态（源、偏移、偏斜、层级、锁定）被采集，前五条才可能被正确对齐。

05　方案：时钟状态把"信号"与"巧合"分开

……获取数据中心里发生之事的证据，其实就是采集更多数据——关于你拥有的事件、以及你时钟状态的数据。在这个例子里，你观察到某块 GPU 出现停滞；然后在另一个节点上观察到某处网络脉冲；而你的计时器可能有某个偏移，如果你不把时间因素算进去，就可能得出错误结论。所以，这就把我们带到"基于证据的采样"。呃，你之前看到的东西——你需要采取的措施——就是采集更多数据，所以……

"getting some evidence about like the stuff that's that's been happening in your data center is actually to collect more more data about like the the events that you have and like the the state of your clocks. So, in this particular example, you have some stalling that you observe for for a GPU. And then you observe a network pulse somewhere on another node and you might have some certain offset for your timers and um your you might get some wrong conclusions if you if you don't account for the timing so and um so this brings us to evidence-based sampling so um you the the stuff that you saw saw before so the measures that you need to take um is to to gather more data so um"

小结　核心示例极具说服力：A 节点 12:00:00.000 的停滞与 B 节点 12:00:00.143 的网络停顿，看似相差 143ms；但 B 节点是 NTP slewing、偏移 +143ms，真实时刻几乎重合。规则由此确立：比较前必须携带 observed_at + 时钟源 + 偏移 + 不确定度。

06　基于证据的采样：六个字段

……你需要把来源考虑进来——主机、设备接口、采集器版本等等。关于时间，你需要看事件被观测到的时刻、被接收的时刻、时钟源、偏移、样本自身的不确定度与新鲜度；然后是值本身。呃，关于语境，你同样需要看真正在跑你 GPU 集群的那些东西；你还需要把它的来源（provenance）算进去——比如工作负载从哪来、这条命令是来自 API 还是别处。呃，所以如果你采集这类数据，你实际上就能拿到关于发生过之事的证据。为此你会走两条路径，所以……

"you need to account for for the source the the host the device interface collector version and so on and so forth and regarding timing you need to look at the the time sense of when an event has been observed when has been received the the source clock the offset certain uncertainty in the sample freshness itself and then the values themselves as well and um so regarding the context again you need to look at the at the at the things that actually running your GPU cluster and you also need to account for the provenance of it so um like where where did workload come from was the command was like from an API or whatnot and um so if you collect this sort of data you can actually get some evidence about the the things that that have been happening and for that you will have two paths so"

小结　六字段构成一个"可审计样本"：Identity（谁报的）、Time（何时、以什么时钟、误差多少）、Value（值与其质量）、Context（在什么工作负载/拓扑下）、Provenance（经何路径、做过何变换）、Rule（不支持就写不支持，绝不编造）。其中 Rule 一条最具工程价值——它把"静默合成"这一常见反模式明确禁止。

07　数据采集：实时路径与取证路径

……实时路径就是纯粹在你的设备上、以及网络状态上做数据采样；第二条路径是取证路径，这条路径更贵一些，它需要被触发，你需要去翻查数据、看发生过什么，并采集某些证据。而这两条路径（输出）遵循同一份 source-bundle 契约。

"the live path is just like pure pure data sampling on on your on your devices and the state of the network and then the second path is the forensic path and this path is a bit more uh is a bit more expensive so it needs to be triggered you need to you need to gather dig through the data what has been happening and there's some evidence that needs to be collected and so both of these paths with the same source bundle contract"

小结　两条路径的成本结构截然不同：实时路径以 1 秒为目标、低成本、连续，靠"新鲜度"决定运维视图是否可信；取证路径按需触发、用 eBPF/NCCL/更深探针，成本高但证据丰富。二者共用 source-bundle 契约，因此可以在同一分析面上拼接——这是"实时看趋势、取证查根因"能成立的前提。

小结　把异构性从"麻烦"翻转为"验证手段"：加速主机、控制器、边缘节点、基础设施服务四类不等的节点，恰好可以检验 schema 在不同能力密度与不同时钟路径下是否仍然成立。作者明确限定这是实验室自建、面向工程迭代的验证，而非生产级基准声明。

10　海量数据摄取：Iceberg 作为开放边界

……所以这是整个项目里我觉得最有意思的部分：你需要采集的数据量是巨大的，对吧？呃，而数据处理领域、或者说数据系统领域总体上，已经有一些创新。呃，所以当你有一个数据中心、想采集时间序列数据时，你最终可能就去用某个 Prometheus 数据库。呃，在我看来，那样是可以的。呃，但它有一些不便之处，比如它不支持 PostgreSQL 方言。呃，最重要的是，当你真正采集数据时，它是按 Prometheus 的方式存的，而不是以开放表格式（open table format）存的。

呃，而当你真正去采集数据、并想把它合并成某种大家都能理解、对数据结构有共识的东西时，你其实可能想用 Apache Iceberg 这样的开放表格式。呃，它可以为更广泛的社区充当一个数据存储，每个人都能用，可以加载进他们的 Snowflake 或 Databricks 流水线。呃，所以这里的整体提议是：对社区，我们提供某种写入优化的、按数据中心划分的存储，你可以装在自己的数据中心里，然后周期性地把这些采集到的数据合并进像 Apache Iceberg 这样的中央数据存储。呃，它可以作为开放分析的基础，支持热数据和冷数据读取。呃，你可以做到引擎无关，而你的整个边界就是这个 Apache Iceberg 数据存储。而且这在 schema 演进等方面也给了你一些灵活性。呃，不过这里最大的改进是：我们能拥有一个更大的数据集合，在其上操作、并识别出某些行为模式。

"so this was the most interesting part of about this entire project for me um is that um, the data that you need to collect is kind of massive, right? And, um, there have been some, uh, innovations in the in the in the data processing space, or let's say like uh, data data systems uh, space in general. And, um, so when you have a data center and you want to collect a time series data, you might eventually just go for some Prometheus data database. And, um, in my opinion, that kind of works. Um, but, um, there are some certain inconveniences that you that you have for Prometheus or instance like it does not support, uh, the post uh, post SQL dialect. And, um, most of all, when you actually collect the data, it's like in the in the way that Prometheus collects it, but it's not like in an open table format. And, um, when you actually go for, uh, the collection of the data and you want to merge it down to, uh, to something that basically every everybody can understand where there's a common understanding of how the data has been structured, you might actually want to go for open table formats like, uh, Apache Iceberg. Um, that can serve for the broader part of the community actually as as some data store that, uh, that everybody can work with and that they can, um, say load to their, um, snow snow flake or data bricks pipeline. And, uh, so the whole proposal here is that, uh, for the community we would provide, um, um, some write optimized per data center storage that the that, uh, say you can you can install within your data center, and then you can periodically merge this data that you collected into, uh, a central data store like Apache Iceberg. Um, that can serve as like the basis for, uh, some open analytics for, uh, hot and cold data reads. Um, you can be engine independent, and, um, your your your whole boundary is just like this, uh, Apache Iceberg data store, um, that you have. And, this also gives you some some flexibility when it comes to like schema evolution and whatnot. Um, however, like the the biggest improvement that we would have here is to um have some uh larger collection of data where on which we could operate and where we could identify certain behavior."

小结　存储架构的关键取舍：不设全局共享的摄取状态（避免跨站点写冲突），每个数据中心各自写优化本地库，再周期性合并到中央 Iceberg。Iceberg 承担"持久、开放交换、schema 演进、快照"的角色，热存则留给实现自选。收益不是更快的查询，而是"更大的可比数据集"——这才是能识别行为模式的前提。

"So, um regarding the the evidence um you would you would essentially just um just look uh about the on the context of of of the of the data that you've been collecting. And you would essentially try to correlate that to to certain parts of your um of of your uh of your data center uh depending on the context. And so, um for instance, um you could try to look at uh the the case that uh maybe your compute is lower than uh than what you might have been expecting."

小结　六级阶梯（单指标→主机对→机架→集群→集群整体→全局基线）规定的是"可比范围"，而不是"分析深度"：范围每扩大一级，就要求更强的一致性（指标与单位、能力 profile、时钟窗口与不确定度、工作负载语境、采集器与 schema 版本）。换句话说，比较范围的上限由语境匹配度决定。

12　示例：为什么有用算力低于预期

所以，呃，举例来说，你可以去看这样一种情况：你的算力可能低于你的预期。那么你会先尝试定位损失出现在哪里——可能在 GPU 上、主机上，你可以通过 BMC 去识别，或者它其实就在网络本身上。

呃，然后你会尝试对齐你的时钟，检查时钟的新鲜度和某些不确定度。接着你会去做佐证（corroborate），看看是否有某些字段并不被支持。然后你会尝试比较你的数据，去验证你认为可能发生的事件是否真的在发生，还是说它只是一个相关而非因果。最后，你可以针对你看到的事件采取行动——根据你实际采集到的证据，采取某些措施、改动参数，或在数据中心里做某些设置。

"for instance, um you could try to look at uh the the case that uh maybe your compute is lower than uh than what you might have been expecting. So, you would first try to locate where uh where the loss appears. That might be um on the GPU, the host, um uh you could try to identify via the BMC or like um could be just located on the fabric itself. And um then you will try to align your clocks um and check about like the freshness and certain uncertainty um in in your clocks. And then you would go over to corroborate um where you would look if you if there are some certain fields that that aren't supported. And then and then you would try to compare uh your your data for the for the evidence about like what what the event that you might think that might have happened. um is actually happening or like if it's just something that's just like a correlation but not really a causation uh thing. And then at the end you can try to act upon the uh the event that you that you saw. And um you can try to take certain measures and change um uh parameters or set up something in your data center depending on the evidence that you actually gathered."

小结　五步工作流把"因果"拆成可执行动作：定位 → 对齐时钟 → 跨通道佐证 → 在可比范围内比较 → 只改证据支持的参数。其中"佐证"这一步专门用来排除假相关；底部的失败处理规则更关键——来源/新鲜度/支持状态/时钟状态任一不成立，就停止、披露、再采集，而不是继续推断。

13　信号的有效性：四道关

……那么，关于信号的有效性，你也可以用分步的方式来处理。你先看你要看的那个节点是否真的暴露了该指标。呃，你可以看样本是否落在精度窗口内——也就是它是否满足你关心的时间上的新鲜度标准。以及时钟状态本身是否有效、可接受。最后你可以看这个值本身是否可追溯。如果你看到所有这些有效性标准都被满足，你其实就可以说：好，它是安全的，可以比较，也可以据此行动。

"you could also handle this in a stepped fashion. So you you go over to look if if a node that you you are looking at actually exposes the metric. Um you could look if the sample inside is inside precision window so if it meets your freshness criteria regarding the the time that you look at. And if if the clock state itself is is valid and acceptable. And at the end you can look if the value itself is actually traceable or not. And if you if you see all of these validity criteria being met you can actually say that okay it's safe and compare to to compare or act upon it."

小结　四道关是有序的短路判断：支持 → 新鲜 → 时钟有效 → 可追溯，任一失败即不进入下一关。这一设计把"这个数能不能用"从经验判断变成可枚举的检查表，也让"不可用"成为一个明确的、可上报的状态，而不是静默的空值。

14　可移植性：三份契约
